# 平台体验升级：实时批改 + 批改驱动的二稿循环（2026-11-22，修订 2）

> 视角：产品负责人（PM）· 交互/UI 设计 · 学习科学 · 平台工程，联合评审稿。
> 范围：① 批改“不够实时”；② “修订稿”让人摸不着头脑。写作为主线，口语、短文字作答同步受益。
> 与 `docs/speaking-ux-optimization-2026-11-22.md` 的关系：该文 P0-1 解决了“状态可信 / 没有死路”，
> **没有解决“快”**；本文接着解决“快”和“改”。诚实契约（不编造分数、T2 关闭、证据可追溯）全部沿用。
>
> **修订 2（2026-11-22）**：代码复核后的闭环版。修订 1 把几项“平台已有的能力”写成了现成可用，
> 实际上没有接线：成本账本、模型调用配额、文字作答的内容规则、多租户心跳、任务释放原语。
> 本版因此重排了交付顺序：**问题卡 schema 与二稿循环先走现有 runner 路径**；
> 流式快评改为在平台前置项和 spike 通过之后才启动。全部评审意见及处置见 §11。
> 本文只做设计与可行性论证，未修改应用代码。

## 0. 一页结论

**诊断**：一份写作批改真正花在模型上的时间约 **11–29 秒**（3 个生产样本，指示性）。
按调度参数推算，学习者平均要 **约 5 分钟** 才能看到结果；这是**模型推算，尚无客户端实测**（§1.3）。
等待的主体不是“AI 在思考”，而是两层轮询叠加的空转：runner 每 5 分钟才醒一次，页面轮询又在第 111 秒后跳到 300 秒。
此外还有一个缺陷：**owner 以外的租户永远看到“批改服务未连接”**，页面轮询被压到至少 60 秒一次（§1.2 D4）。

“修订稿”的困惑源于同一个根因：**首稿一提交就进入修订，但批改还没到**。
批改又是一整段没有原文锚点的散文；二稿被当作一篇新作文重新批改，批改者看不到首稿。

**方案一句话**：
> 提交 → 很快出现锚定到原文的问题卡 → 带着问题卡改二稿 → 每条问题得到“改好了吗”的判定。

| 目标 | 现状 | 目标值 | 何时可验收 |
|---|---|---|---|
| 写作：排队等待（任务创建 → 被领取） | 推算均值约 150 s，最坏约 300 s | **p90 ≤ 15 s** | 第 0 期 |
| 写作：结果可见（任务创建 → 页面渲染） | 推算 p50 约 5 分钟，最坏约 10 分钟 | **p50 ≤ 45 s**（第 0 期）→ **首卡 p50 ≤ 8 s**（第 2 期） | 0 / 2 |
| 口语：排队等待 | 同上 | **p90 ≤ 15 s** | 第 0 期 |
| 口语：结果可见 | 处理时间历史实测 77–162 s，另加排队 | 拿到 N ≥ 10 的基线后再定目标 | 第 0 期出基线 |
| 二稿：知道要改什么 | 无锚点、无清单 | 问题锚定到原文，可勾选 | 第 1 期 |
| 二稿：知道改好没有 | 新作文式重批 | 逐条判定：已解决 / 部分 / 未解决 / 未改动 / 新问题 | 第 1 期 |

**交付顺序**（§7）：
- **第 0 期**：调度、心跳、打点；
- **第 1 期**：问题卡 + 二稿循环，走现有 runner，不新增密钥和基础设施；
- **第 2 期**：流式快评，需先完成平台前置项 + spike。

第 0、1 期合起来已经能解决用户提出的两个问题；第 2 期把“快”从几十秒推到几秒。

### 1.3 用户看到结果的时间（模型推算，待第 0 期打点替换）

runner 相位均匀分布在 0–300 s，加上约 27 s 处理时间，结果就绪时刻 T ∈ [27 s, 327 s]。
页面的累计检查点为 3、6、11、21、51、111、**411** s（`studio.tsx:201,216`；任务计数变化时会重新从 3 s 开始一次）。

- T ≤ 111 s 的概率约 28%：在 111 s 内看到；
- 其余约 72%：要等到 **411 s** 那次检查（切回页面触发的 `focus` 唤醒除外）。

**期望可见时间 ≈ 0.28 × 75 + 0.72 × 411 ≈ 317 s ≈ 5.3 分钟**；最坏 ≈ 300 + 27 + 300 ≈ 10.5 分钟。
其他租户还要叠加 D4（轮询间隔至少 60 s）。

## 2. 设计原则（联合评审共识）

1. **“实时”指的是提交之后，不是边写边批。** 独立首稿是记录真实水平的唯一依据，首稿阶段只给确定性、与内容无关的信息。
2. **先出可执行的那一条，再出完整报告。** 用户感知速度看的是首条反馈的到达时间。
3. **展示过的内容不撤回。** 流式的单位是**已校验并已持久化**的问题卡，不是 token；已展示的卡不可改写（§4.6）。
4. **锚点由服务端解析。** 模型只给引文，位置由服务端在原文中计算；对不上的问题降级为整体建议，绝不伪造位置。
5. **“已改动”不等于“已改对”。** 是否改动由本地 diff 确定；是否改好只能由批改判定，并标注来源。
6. **先提示，后答案。** 参考改法默认折叠，展开会被记录；指标单独统计没有展开参考答案就改好的问题。
7. **一个循环只有一个主行动**；**降级不留死路**（沿用 P0-1 状态机）。
8. **所有批改路径执行同一套规则**：内容规则、成本、配额、同意与权益都由服务端的完成路径统一把关，不依赖生产者自觉。

## 3. 目标体验

### 3.1 写作：四步循环（替代“首稿 / 修订稿”）

```
① 独立首稿 ──► ② 读批改 ──► ③ 改二稿 ──► ④ 对照复盘
  (无 AI)      (问题卡)      (带问题卡)    (逐条判定 + 下次带走一条)
```

步骤条常驻页面顶部，用语统一为：**首稿 / 批改 / 二稿 / 复盘**（§5.4）。

#### ① 独立首稿：即时、确定性的写作仪表

```
┌ 首稿 · Task 2 ─────────────────────────────── ⏱ 23:41 / 40:00 ┐
│ [题目]                                                          │
│ ┌────────────────────────────────────────────────────────────┐ │
│ │ (输入框)                                                    │ │
│ └────────────────────────────────────────────────────────────┘ │
│ 212 / 250 词 · 4 段 · 平均句长 17 词 · 已保存在本机 14:02      │
│ 自查清单（自我陈述）：□ 回应题目两部分 □ 明确立场 □ 结论段      │
│        [ 保存到云端 ]                [ 提交首稿并开始批改 ]       │
└─────────────────────────────────────────────────────────────────┘
```

- 字数、段落数、句长、计时都在本地计算，不调用模型。
- “提交首稿并开始批改”如实反映现状：提交时就已经自动排队（R2 改的是文案，不需要新增功能）。
- “保存到云端”保留现有的服务端草稿写入，用于换设备继续（D10）；本机自动保存另外如实标注。

#### ② 读批改：问题卡

```
┌ 批改 · 已到达（6 条）  ← 第 2 期：正在生成（已出 3 / 约 6 条）──┐
│ 首稿（只读，标注）                     │ 问题卡                     │
│ Nowadays many people [believes]① that │ ① 语法 · 必改             │
│ ...[the government should to]② ...    │   主语是复数，谓语要怎么变？│
│                                        │   ▸ 查看参考改法           │
│                                        │ ③ 论证 · 建议             │
│ 本稿优先：① 主谓一致  ③ 论据具体化      │   第二段论据缺少具体例子… │
│                                        │   （只给方向，不代写）      │
│                        [ 开始改二稿（已选 2 项）]                    │
└─────────────────────────────────────────────────────────────────────┘
```

- 第 1 期：问题卡由 runner 一次性写回（第 0 期之后约 30–45 s 到达）；等待时显示文字任务专用的真实阶段
  （排队 → 生成 → 校验），不再出现“读取原录音”（R11）。
- 第 2 期：问题卡逐条到达；顶部只显示事实性的进度（“已出 3 条”）。
- 每张卡：类别（任务回应 / 连贯 / 词汇 / 语法）、优先级（必改 / 建议 / 可选）、中文原因或提示问句。
  语法和词汇卡的参考改法默认折叠，**展开会被记录**（原则 6）。论证和结构卡**只给方向，不代写**。
- “本稿优先”最多 2 条，默认勾选。

#### ③ 改二稿：带着问题卡改

```
┌ 二稿 ────────────────────────────────────────────────────────────┐
│ 编辑器（以首稿为底稿；勾选问题的锚点高亮）   │ 本次要改（2）        │
│ Nowadays many people believe that ...        │ ✓ ① 已改动 · 待复核  │
│                                              │   为什么这样改：      │
│                                              │   [people 是复数____] │ ← 必改项一句话（必填）
│                                              │ ○ ③ 未改动           │
│                                              │   [我改好了吗？] 4/5  │
│ 改动 7 处 · 214 词                            │ 补充说明（选填）     │
│        [ 保存到云端 ]              [ 提交二稿并复核 ]               │
└──────────────────────────────────────────────────────────────────┘
```

- **自我解释保留，但大幅缩小**：只要求对勾选的“必改”项写一句“为什么这样改”（≥ 4 个字符），其余选填。
  这样既保留自我解释带来的学习收益，又不必先自己诊断（R5）。`writeFocus` 由这些句子拼接生成。
- **“已改动”的判断**：以首稿到二稿的词级 LCS 对齐为准。锚点范围内有任何词被增删改，就显示“已改动 · 待复核”；
  不会因为同一个词在别处再次出现而误判（§4.4）。
- **“我改好了吗？”单项快检**：只判断这一条问题，结果为已解决 / 部分 / 未解决加一句理由，
  标注“单项快检，以提交后复核为准”。每份二稿限 5 次（服务端计数）；每次调用留下可追溯记录（§4.5），
  并在复核和复盘中如实显示“本稿使用了 n 次快检”。第 1 期快检走 runner 队列，约十几秒；第 2 期改为秒级。
- 完成门槛：服务端保持现有的结构性校验（二稿 ≠ 首稿，且 `writeFocus` 非空），后者现在由学习者写的一句话满足；
  教学性门槛（至少一个勾选锚点被改动）由客户端执行，并作为数据记录，不在服务端强制（§4.7）。

#### ④ 对照复盘：改好了没有

```
┌ 复盘 ────────────────────────────────────────────────────────────┐
│ 逐条判定                        │ 差异视图（词级）                   │
│ ① 主谓一致     ✅ 已解决（未看参考）│ many people ~~believes~~ believe │
│ ③ 论据具体化   ◐ 部分：例子有了，但没和论点连起来                    │
│ ② should to    — 本次未选，未改动                                    │
│ 新出现 1 条：④ 冠词 · 建议                                           │
│ 本稿使用了 2 次快检                                                  │
│ 下次带走一条：写完每个论点后补一个“例如……”的具体例子                 │
│                                     [ 进入今日复盘 → ]               │
└──────────────────────────────────────────────────────────────────┘
```

二稿复核按首稿的批改状态分三种情况处理（§4.8），复核时看得到首稿（R8）。

### 3.2 口语

口语的声学证据（Stage A、检测器）必须在本机 runner 上运行。“实时”分三层：

1. **去掉调度空转**（第 0 期）：排队等待从约 150 s 降到 ≤15 s。端到端时间由处理时间（历史 77–162 s）决定，
   第 0 期先拿到 N ≥ 10 的基线，再设目标。
2. **真实阶段可见**：阶段来自检查点写入（D8），沿用现有的 `stageLabel`；同时引导学习者先回听录音、对照自查。
   不显示任何估算分数。
3. **分段放出**（第 3 期，可选）：文字层反馈先到，声学层随后到；需要新的部分写回契约，单独评审。

## 4. 技术方案与可行性

### 4.1 方案比较

| 方案 | 首条反馈 | 规模 | 新基础设施 | 结论 |
|---|---|---|---|---|
| A. runner 常驻 + 服务级心跳 + 紧轮询 | 文字约 30–45 s | M（4–6 天） | 无 | **第 0 期** |
| B. 问题卡 schema + 二稿循环（runner 路径） | 同 A | M–L（2–2.5 周） | 无 | **第 1 期** |
| C. 流式快评（Durable Object 执行，SSE 订阅） | 约 5–8 s | L（2–3 周，含前置项） | Worker 密钥、DO | **第 2 期**，前置项和 spike 通过后启动 |

### 4.2 第 0 期：调度、心跳、打点

**① 服务级心跳**（修复 D4，所有租户都受益）
- runner 心跳同时写入 `service_heartbeats`（`lib/metrics.ts:187`）；`coachData` 对所有租户读取服务级心跳来判断 `connected`，
  租户级心跳只用于 owner 的诊断。
- 回归测试：非 owner 租户在 runner 在线时看到 `connected=true`，并且不会读到其他租户的任何数据。

**② runner `--daemon` 模式**（D6：这是新建，不是“复用已有循环”）
- 单进程常驻，整个生命周期持有 flock；一次 `run_multi_tenant` 结束后进入空闲等待，再开始下一轮。
- 空闲时等待 **2 → 4 → 8 → 10 s** 退避（上限 10 s），领到任务后立即重置为 2 s。
- 心跳每 60 s 一次，与领取解耦（不再每轮发 started / finished 两次）。
- UTC 跨日时重载预算；收到 SIGHUP 时重读配置和凭据文件。
- **最长寿命**：运行 6 小时或处理 200 个任务后正常退出，由 launchd `KeepAlive` 拉起，以保留“进程新鲜”的性质，
  避免长时间运行的内存问题。
- launchd 改为 `KeepAlive=true`，保留 `StartInterval` 版 plist 作为一键回滚；生产副本 `~/.bandroom-runner-prod/` 同步更新。

**③ 请求和写入预算**（修复 D7 的低估）
- 服务端：空队列的领取不写审计行（只计数）；限流行按分钟桶合并写入。
- 估算（空闲上限 10 s）：每天约 8,640 次领取 + 1,440 次心跳 ≈ **1.0 万次请求/天**；写入 ≈ 1.0 万限流 + 1.4 千心跳 +
  领取前的 `markExhaustedGlobal` 扫描（无匹配行时不产生写入）≈ **1.2 万行/天**。
  免费层上限分别为 Workers 10 万次请求/天、D1 10 万行写入/天。
- 空闲时单次等待均值约 5 s，满足“排队 p90 ≤ 15 s”。
- 可选优化：服务端长轮询（`waitMs ≤ 20000`）可以把请求再降一个数量级，但需要先确认当前 Workers 计划下的 CPU 限制，放到 §4.9 spike。

**④ 页面轮询**（`app/studio.tsx`）
- 有 `queued` / `running` 任务且服务级心跳在线时：每 2 s 检查一次，最长 3 分钟，之后回到现有退避，去掉“111 s → 411 s”的断崖。
- 文字任务改用专用阶段 `queued → generating → validating`（修复 D8 / R11）。

**⑤ 打点**（修复“推算当实测”）
- 服务端已有 `created_at` / `claimed_at` / receipt `created_at`；新增客户端 `rendered_at` 信标（只上报 attemptId 的哈希和时间戳）。
- 采样量不足时，在 QA 环境用合成账号定时提交合成作文和合成录音作为探针（不使用真实学习者内容）。

**验收**：文字 N ≥ 20、口语 N ≥ 10（真实任务加探针）：排队等待 p90 ≤ 15 s；文字可见时间 p50 ≤ 45 s；
非 owner 租户 `connected` 正确；口语端到端基线入档。

### 4.3 第 1 期：问题卡 + 二稿循环（runner 路径，无新基础设施）

先在现有 runner 路径上交付问题卡 schema，再在第 2 期叠加流式。好处：
- 锚点命中率、提示质量、二稿指标可以在**真实输出**上先测出来；
- 不新增密钥，不受第 2 期 spike 结果影响；
- 用户的第 ② 个问题（修订稿）在第 1 期就能完整解决。

服务端必须先完成的改动：
1. **内容规则统一**（D2）：把 `runner/content_rules.py` 中文字作答的规则（attempt id 回显、必须引用学习者原文、
   文字作答不得谈发音）移植到 `lib/content-rules.ts`；新增“禁止输出写作分数”的规则；
   在 `complete_review_task` 和 `add_coach_feedback` 中对**所有 stage** 执行。Python 侧保留作为早期拒绝。
2. **独立的 `writing` 字段**（D3）：新增 `writing` 输入（zod schema `bandroom-writing-feedback-v1`），不复用 `analysis`；
   receipt 的输出摘要升级版本号（`review-tasks.ts:436-452`），保证重放幂等；页面按 kind 分支渲染，
   避免把写作当成口语渲染。
3. **批改上下文**（D9）：`writeRevision` 的上下文加入首稿原文、首稿 receiptId 和问题卡（如果有）。

### 4.4 问题卡数据契约 `bandroom-writing-feedback-v1`

```jsonc
// 模型输出（每行一个对象；第 1 期整批写回，第 2 期逐行流式）
{"type":"issue","id":"i1","category":"GRA","priority":"must",
 "quote":"many people believes","context_before":"Nowadays ",
 "prompt_zh":"主语是复数，谓语要怎么变？","why_zh":"主语 people 为复数，谓语用原形。",
 "suggestion":"many people believe"}
{"type":"issue","id":"i3","category":"TR","priority":"should",
 "quote":"It is good for society.","context_before":"",
 "prompt_zh":"“好”具体体现在哪里？能举一个例子吗？","why_zh":"论点缺少具体例子。","suggestion":null}
{"type":"summary","priorities":["i1","i3"],"next_step_zh":"每个论点后补一个具体例子。"}
```

**服务端校验**（锚点由服务端负责，原则 4）
- `quote` 必须在原文中逐字出现。出现多次时用 `context_before` 消歧；仍有歧义或找不到就去掉锚点，降级为整体建议。
  服务端写入 `{start,end}` 字符偏移，不使用模型给的出现次数。
- `category ∈ {TR, CC, LR, GRA}`；`TR` / `CC` 的 `suggestion` 强制为 null（不代写）。
- 任何字段都不得出现雅思分数（统一内容规则，§4.3-1）。
- 兼容：`feedback` 文本字段继续由问题卡拼接生成，旧页面和 MCP 读者不受影响；旧的散文反馈照旧渲染。

**二稿中的锚点追踪**：首稿到二稿做词级 LCS 对齐，把锚点区间映射到二稿：
- 区间内的词全部原样对齐 → `untouched`；
- 有增删改 → `changed`。

这是本地、确定性、零成本的判断。

### 4.5 单项快检（`recheck`）

- 输入：问题卡、首稿锚点区间、二稿对应片段（按 LCS 映射）、学习者写的“为什么”。输出：`resolved | partial | unresolved` 加一句理由。
- 每次调用写一条 `review_rechecks` 记录（输入哈希、issue id、结论、模型、promptVersion、成本），满足“证据可追溯”。
- 每份二稿最多 5 次，由服务端按 `attemptId` 计数；第 1 期作为一种轻量任务走 runner 队列。
- 二稿复核会收到快检次数和结论，作为背景，不当作结论直接采用；复盘页面如实展示。

### 4.6 二稿复核契约

```jsonc
{"type":"verdict","issue":"i1","result":"resolved|partial|unresolved|untouched","evidence_quote":"many people believe","why_zh":"..."}
{"type":"issue", ... }            // 二稿中新出现的问题
{"type":"summary","carry_forward_zh":"..."}
```

- 确定性判断优先：LCS 判为 `untouched` 的问题，模型不得判为 `resolved` / `partial`，服务端会改写为 `untouched`。
- 给出 `resolved` / `partial` 时，必须引用二稿原文作为 `evidence_quote`，并且服务端能逐字校验；否则降级为 `unresolved`。
  这是为了防止复核迎合学习者。

### 4.8 二稿复核的路由

### 4.9 第 2 期：流式快评（启动条件 = 前置项 + spike 全部通过）

**架构**：生成过程与 HTTP 连接解耦。

```
浏览器 POST /api/review/stream {attemptId}
  └► Worker：鉴权 → 同意 / 权益（inline_review）→ 配额（recordModelCall）→ D1 成本预留
           → claim_review_task_by_id(taskId, kind='inline', lease=45 s，可续租)
           → 唤醒该任务的 Durable Object（ReviewRun）
ReviewRun DO：调用 DashScope（stream）→ 每行：解析 → 锚点 → 内容规则 → 持久化为卡片检查点 → 推送给订阅者
           → 全部完成：complete_review_task（必须原样包含所有已发布的卡片）→ 记账 / 退款
浏览器：SSE / WebSocket 订阅 DO；刷新或断线后，先读已持久化的卡片，再继续订阅
失败：DO 调用 release_review_task(fence)（不消耗领取次数），回到 queued，由 runner 接手；
      runner 的 snapshot 中带上已发布的卡片作为“不可改写的前缀”，runner 只补全剩余部分
崩溃：45 s 租约过期后，任务回到可领取状态（如实说明：崩溃时的兜底时间约 45 s + runner 空闲等待）
```

**平台前置项**（全部完成后才进入实现）

| # | 前置项 | 解决的问题 |
|---|---|---|
| P1 | D1 成本账本成为唯一来源：runner 通过 MCP 的 `reserve_cost` / `refund_cost` 记账；新增全局行；接上 `recordModelCall` | D1：避免两套账本、两套上限 |
| P2 | `release_review_task(fence)`：释放回 `queued`，不消耗次数 | D5 |
| P3 | `claim_review_task_by_id` 加 `claim_kind='inline'`；启用 inline 时，文字任务创建时设置 `next_at = now + 20 s` 作为保留期，runner 在保留期内领不到；双向竞争各有一组测试 | 与常驻 runner 的竞争 |
| P4 | 卡片检查点表，加上“已发布卡片不可改写”的完成校验 | 已展示内容不撤回 |
| P5 | 权益新增 `inline_review`（`lib/entitlement.ts:21`），作为按租户的开关和紧急关闭手段 | 灰度和止损 |

**Spike（1–2 天，任一项不通过就停在第 1 期，或改走“runner 流式回写 → DO 中转”）**
1. 从 Cloudflare 边缘到 `dashscope.aliyuncs.com` 的首 token 时间和稳定性（20 个样本）。
   国际站端点不是可以直接替换的备选：账号、密钥、模型可用性和价格都可能不同，并且学习者文本会从边缘出境。
   如果要采用，必须更新隐私说明。
2. 在 vinext + Cloudflare Access 下，SSE 或 WebSocket 能否透传；DO 能否在当前部署中绑定；当前 Workers 计划的 CPU 和时长限制。
3. 用 20 篇**合成样例**作文测问题卡提示词：锚点命中率 ≥ 90%，人工评审认为质量不低于第 1 期的真实输出。
4. 密钥以 Worker secret 存放，使用最小权限的子账号密钥；写好轮换流程；日志沿用 redaction 规则脱敏。

**成本**（与 runner 现有估算一致）：首稿 0.05 元 + 二稿复核 0.05 元 + 快检 ≤ 5 × 0.01 元 ≈ **每篇 0.15 元**。
单用户 2 元/天的上限足够约 13 篇；全局上限由 P1 统一执行。

  - 第 2 期：领取 → 发布卡片 → 断线 → 重新订阅；DO 失败后 `release` → runner 补全，已发布卡片保持不变；
    租约过期后回收；inline 与 daemon 的双向竞争；D1 成本账本在两条路径上共同执行上限。
- **runner**（`pytest runner/tests`）：daemon 的空闲退避、跨日、SIGHUP、最长寿命退出、flock、熔断、预算暂停。
- **契约**：`tools-list` 快照、`security-matrix`、`tenant-isolation`、`backup` / `migrate-export` / `dsr` 新字段往返。
- **浏览器**：Playwright 覆盖四步循环的桌面和移动布局、键盘锚点导航、参考改法展开记录、降级态文案。
- **回归**：`pnpm run test:review`、`test:pronunciation-coach` 全量通过；旧散文反馈的渲染不变。

## 9. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 锚点不准 | 服务端解析加上下文消歧；对不上就降级；命中率 < 80% 自动隐藏锚点界面 |
| 学习者照抄参考改法 | 先提示，后答案；记录展开；单独统计“未看答案的解决率” |
| 复核迎合学习者 | `untouched` 优先；必须逐字引用二稿作为证据；抽样人工审核 |
| 两条路径不一致（第 2 期） | 共用 receipt 表、内容规则、D1 账本和 promptVersion；receipt 记录 `producer`；已发布卡片不可改写 |
| 常驻 runner 资源泄漏 | 最长寿命自动重启；回滚 plist 随时可用 |
| 免费层配额 | §4.2 预算约 1 万请求 + 1.2 万写入/天；在 metrics 中加入日用量告警（80%） |
| 本机休眠 | 服务级心跳如实显示“未连接”；长期可迁到常开主机（systemd 模板已在 `runner/cron/`） |
| 新密钥暴露面（第 2 期） | Worker secret、最小权限子账号密钥、轮换流程、`inline_review` 开关 |
| 学习者文本出境路径变化（第 2 期） | spike 中确认端点地域；如有变化先更新隐私说明 |

## 10. 明确不做

- 首稿阶段不提供任何 AI 内容提示。
- 不输出写作或口语的雅思分数估计（未校准），并由服务端规则强制。
- 不重新开启 T2 音素断言；口语分段放出不引入新的发音结论。
- 不使用浏览器 Web Speech API 或第三方实时转写。
- 不代写论证和结构段落。
